# S0：software-only 对照的搜索与依赖限制（P7 Step 10；PDF §15.1 判据 2）

> PDF 原文：「**软件对照（S0）须核查**：当前官方版本、常数处理、×1 提取、寄存器调度与既有 ISA 可表达性。**若尝试后没有更快的软件版，给出尝试和依赖限制；不要承诺一定能得到新的软件周期。**」

**结论先行**：本次**未找到、也未实现**比官方实现更快的**同安全等级**软件版 ⇒ 按 PDF 的允许路径如实记录搜索过程与依赖限制（下列五项逐项给证据）。官方实现本身即是我们的 baseline（B0，P0 冻结）⇒ 「仅战胜未优化软件」这一质疑不成立：B0 = 官方代码 ✓。

## 1. 当前官方版本（读的是哪份）

- `sw/otbn/crypto/p256_base.s`（2219 行）—— 坐标算术与 `mul_modp`；`p256_shared_key.s`（ECDH 上层）。**本节只读，不修改任何 `sw/` 文件** ✗。
- baseline = P0 冻结的 `run_p256.elf`（sha256 `f4d64e80…`，36,732 B）+ 其 chip 日志（`$run_dir/rtl/test_p256_only.trace.uart0.log`）⇒ 对照物可复现 ✓。

## 2. 常数处理

- `setup_modp` 每次标量乘**起始装一次**：`MOD ← p`、`w28 ← r256`、`w29 ← r448`（`scalar_mult_int` 第 1300–1303 行处的调用 ✓）⇒ 循环内**不重复装载** ✓。
- 约简用 `bn.addm`（对 `p` 的模加）+ 现成的 `r256/r448` 常数；**减法项**刻意不存表，改写为 `bn.sub` 的移位链（源码注释给了理由：负项 ~224 位比正项 ~256 位更快）⇒ 常数侧已是最省 ✓。

## 3. ×1 提取与阶梯结构

- 阶梯 = **二进制 double-and-add**，`loopi 321, 63`（= 320 位 + 1 次收尾 ✓）：每迭代**1 次 `proj_double`** + **按标量位条件 1 次 `proj_add`** ✓。
- 标量位/中间值逐次用 `bn.wsrr … URND` 随机化后再提取（SCA 加固），**不是**追求速度的写法 ✓。
- ⇒ **321 次 double 是结构下界**（256 位标量无论二进制还是 w-窗口都要 255–256 次 double ✗窗口省不掉它）；可减的只有 `proj_add` 的次数（窗口法 ~160 → ~60）⇒ 那需要**预计算表**，并会改变逐操作 URND 掩码的安全策略 ⇒ 属**安全—性能权衡**，不是「白捡的软件优化」✗。

## 4. 寄存器调度与指令选择（`mul_modp` 本体，逐项计数）

- 静态规模：**52 条 `bn.*`** —— `bn.mulqacc`×18、`bn.mulqacc.z`×2、`bn.mulqacc.so`×2、`bn.mulqacc.wo`×2、`bn.addm`×8、`bn.add`×7、`bn.sub`×5、`bn.rshi`×3 ⇒ 每次都把 MAC 装满（`mulqacc` 及其 `.z/.so/.wo` 变体共 26 条），写回只在与约简衔接处做（`.so`/`.wo` 就是为此而用）✓。
- 累加链**串行依赖**（每条 `mulqacc` 累加到同一 ACC ⇒ 必须等上一条出结果）⇒ 该等待是**结构性**的，软件层无法消除（除非改算法/数据流 ✗）✓。
- 实测（B1 用的同一份旧 app，新 RTL 上与基线逐位一致 ✓）：每次 ECDH = **581,607 条指令 / 796,312 周期** ⇒ **1.37 cycles/insn**，即约 **27%** 的周期是等待 ✓ —— 与上面的结构判断一致。
- 调用规模：每次 ECDH ≈ **9,599 次 `mul_modp`**（§8.12 实测调用数）⇒ 平均 60.6 条指令/调用（= 52 条本体 + 调用与循环开销 ✓，两者吻合）。

## 5. 既有 ISA 可表达性

- 官方已用到最强的 MAC 形式（`bn.mulqacc` 的 `.z/.so/.wo`）、`bn.addm/subm`、`bn.rshi`、`bn.subb/addc`、`bn.mov/addi`、`bn.lid` —— 本任务所需的算术形式**在既有 ISA 内已表达完毕** ✓；没有「存在但未用」的指令可捡 ✗。
- 与我们的新指令对比：A1 的收益来自**硬件**（合并归约 + 6 拍窗口），不是「用了更好的软件写法」 ✓ —— 这正是 B0/A1 对照要证明的事 ✓。

## 6. 尝试与依赖限制（如实记录）

| 候选项 | 是否可做 | 卡在哪 |
|---|---|---|
| 指令级重排 / 消冗 | ✗ 无空间 | `mulqacc` 串行累加同一 ACC ⇒ 等待是结构性的；本体已 52 条、常数已预装 ✓ |
| 窗口法（w=2/4）减少 `proj_add` | 需实现 + 需改安全策略 | 需要预计算点表；且要改动官方**逐操作 URND 掩码**的加固写法 ⇒ 安全—性能权衡 ✗ |
| 改动阶梯本身 | ✗ 受限 | 阶梯在 `sw/otbn/crypto/*`（**本任务不改任何 `sw/` 文件** ✗）；要做只能把阶梯复制进我们包再改 + 重新过 KAT/协议测试 ⇒ 记为依赖限制 |
| 换更快的点公式（如 Jacobian → 其他坐标） | ✗ 超范围 | 会改变域运算次数与 KAT 口径 ⇒ 不是「同一算术的软件优化」✗ |

⇒ **结论**：软件侧（调度、常数、指令选择）**已无空间**；结构侧的可行手段都要么改安全策略、要么改 vendored 代码/算术口径 ⇒ 按 PDF 判据 2 的允许路径**如实记录** ✓，**不承诺**存在更快的同安全等级软件版 ✗。
